# DIP 3.0 分组器 · 局域网数据更新方案

> 适用对象：绿色版桌面客户端（`dist/DIP3-Desktop/`）在院内局域网多台电脑上使用，
> 需要「一处更新、多端生效」的数据同步。
> 结论先行：**推荐「数据分发中心」方案（服务器做数据主库 + 客户端增量拉取）**，
> 以「数据更新包」作为离线兜底；共享目录方案只在极少数场景下才考虑。

---

## 一、先分清：哪些数据要更新

这是整个方案的地基。**业务数据可以下发，本机个性化数据绝对不能下发** —— 很多
「共享目录」方案就是在这里翻车的（一共享，全院的主题、账号口令、我的收藏互相覆盖）。

| 文件 | 体积 | 内容 | 产生方式 | 能否下发 |
|---|---|---|---|---|
| `config/dip3-config.json` | 1.6 MB | 病种库（先期/并项/基础/基层/烧伤/肿瘤/结核/排除） | 后台导入 Excel | ✅ 可下发 |
| `data/config-meta.json` | 1 KB | 病种库导入元信息（时间/来源/各表条数） | 随上一条生成 | ✅ 必须与病种库**成对**下发 |
| `data/mappings.json` | 6.8 MB | ICD-10 ↔ 医保编码映射（含灰码） | 后台导入 | ✅ 可下发 |
| `data/zonghe.json` | 0.1 KB | 综合病组规则 | 后台导入 | ✅ 可下发 |
| `data/lixiang.json` | 1.9 MB | 立项指南 + 解读辅导 Q&A | 后台导入 | ✅ 可下发 |
| `data/dezhou-price.json` | 1.7 MB | 德州物价 + 类别使用说明 | 导入物价包 | ✅ 可下发 |
| `data/guifan.json` | 11.1 MB | 全国医疗服务项目技术规范（2023） | 只读资料 | ✅ 可下发（体积大，懒加载） |
| `data/settings.json` | 0.3 KB | 软件名称 / 主题 / 后台账号口令 / 托盘开关 | 本机后台配置 | ❌ **本机私有** |
| `data/dezhou-favorites.json` | 小 | 「我的收藏」（常用物价） | 本机点星标 | ❌ **本机私有** |

> 即：**`data/` 目录里混着两类东西**（业务数据 + 本机私有配置），任何同步方案都必须先把这两类拆开。
> 建议顺带做一次拆分：把 `settings.json` 与 `dezhou-favorites.json` 迁到
> `%LOCALAPPDATA%\Dip3Grouper\`，`data/` 从此只放可共享的业务数据。

## 二、四种方案对比

| # | 方案 | 做法 | 开发量 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|---|---|
| 1 | **共享目录（UNC）** | 服务器共享 `data/`、`config/`；客户端 `DIP3_HOME` 指向 `\\server\share` | 小（约 60 行） | 零分发，改完重启即生效 | 必须常联网；11 MB 共享盘读盘慢；无校验、无回滚；任何一台机器误写就污染全院；必须先拆本机私有数据 | 3~5 台、数据几乎不变 |
| 2 | **数据分发中心** ⭐ | 服务器放数据主库 + 只读分发接口；客户端「检查更新」→ 只拉变更文件 → SHA-256 校验 → 备份 → 原子替换 → 热重载 | 中（约 400 行） | 增量传输、有校验、自动备份可回滚、断网仍可用本地数据、只开一个 TCP 端口、不需要文件共享权限 | 需要一台常开机器 + 写代码 | ≥5 台、数据会持续更新 |
| 3 | **纯 Web 模式** | 服务器跑 `Dip3Grouper.Web`，医生用浏览器访问 `http://server:3210` | 零 | 数据天然只有一份，管理员在服务器上更新，全院自动同步；无客户端要维护 | 必须走浏览器；断网即不可用；桌面端的托盘、离线收藏等能力用不上 | 网络稳定、能接受浏览器操作 |
| 4 | **数据更新包** | 服务器导出 `数据更新包.zip`（含 `manifest.json` + 各数据文件），客户端后台一键导入 | 小~中 | 简单可控、可 U 盘带到无网机器、天然带版本 | 手动、需逐台操作 | 低频（月度/季度）、离线环境 |

**推荐组合：方案 2 打底（日常自动），方案 4 兜底（离线/应急）。**
两者共用同一套「清单 + SHA-256 + 备份替换」内核 —— 实现一次，两种形态同时具备。

## 三、推荐架构（方案 2）

```
┌── 服务器（一台常开机器，可复用现成的 Dip3Grouper.Web，端口 3210）──────────┐
│   ① 管理员照常走后台导入（Excel / 物价包）→ 写入该机 data/ + config/        │
│   ② 数据主库：data/*.json + config/dip3-config.json                        │
│   ③ 新增只读分发接口（白名单内文件）：                                       │
│        GET /api/data/manifest      → { generatedAt, files:[{name,sha256,size,updatedAt}] }
│        GET /api/data/file/{name}   → 文件字节流                             │
└────────────────────────────────────────────────────────────────────────────┘
                              │  局域网 HTTP
                              ▼
┌── 客户端（每台电脑的绿色版本地目录）──────────────────────────────────────┐
│   ① 检查更新：拉 manifest                                                  │
│   ② 比对差异：逐文件比 SHA-256，只挑出不一致的                                │
│   ③ 下载替换：下载到 data/.staging/ → 校验 → 备份旧文件 → File.Replace 原子替换 │
│   ④ 热重载：AppState.ReloadAll()，无需重启程序                              │
│   备份目录：data/_backup/20261007-1856/  ← 出错或想还原时一键回滚             │
│   连不上服务器 → 照常用本地数据（离线不降级）                                  │
└────────────────────────────────────────────────────────────────────────────┘
```

**为什么不用共享目录：** 网络盘上没有「原子替换 + 校验」的概念，`File.Replace` 跨 SMB
行为不可靠；而且客户端启动时要读 11 MB 的 `guifan.json`，走网络盘会明显拖慢启动。
HTTP 拉一次落本地，之后全走本地磁盘，速度和单机版一样。

## 五、必须守住的几个细节

1. **病种库与元信息成对更新**：`config/dip3-config.json` 与 `data/config-meta.json`
   必须同批替换，否则后台「概览」的条数统计与实际配置对不上。
2. **原子替换**：复用现成的 `Js.AtomicWrite` / `File.Replace`（先写 `.tmp` 再换），
   避免中途断电留下半截 JSON —— 这类文件一旦损坏，客户端直接起不来。
3. **`guifan.json` 是懒加载**：11 MB，替换时机上建议放在客户端空闲或提示用户
   「更新后请重新打开技术规范页」，避免正在读时被替换（Windows 下文件被占用会导致替换失败，需重试）。
4. **只读接口防路径穿越**：`/api/data/file/{name}` 只从白名单常量里取路径，
   不接受任何拼接出来的相对路径。
5. **收藏/主题/口令不回传、不覆盖**：客户端 → 服务器方向的写操作一律不做，
   避免出现「双向同步冲突」这类无解问题。
6. **防火墙**：服务器放行 3210 入站即可，局域网内走 HTTP 足够；不需要开文件共享。
7. **回滚**：每次更新前把被替换的文件原样拷到 `data/_backup/<时间戳>/`，
   保留最近 5 次，后台提供「还原到上一次」。

## 六、程序本体升级（顺带说清）

数据可以热更新，但 `exe` / `dll` 在运行中无法替换。程序升级建议单独走：

- 新版本 zip 解压到**新目录**，桌面快捷方式指过去；
- 客户端启动时通过同一个分发接口读一个 `app-version.json`，发现服务端版本更高就提示
  「有新版本，请使用新版程序」，**不做自动替换**（自动替换在杀软/权限环境下不可靠）。

数据与程序版本分开治理，是这类院内工具最省心的做法。

## 七、一句话决策

- 机器多、数据会持续更新（物价调价、病种库更新、解读辅导追加）→ **方案 2 + 方案 4**
- 机器少、数据基本不动 → 方案 1（但必须先拆本机私有数据）
- 允许医生用浏览器 → 方案 3 最省事，连客户端都不用装

## 八、落地实现（2026-10-07 已交付，方案 2 + 方案 4）

**服务端**（跑 `Dip3Grouper.Web` 的那台机器，端口默认 3210，无需任何额外配置）：

| 接口 | 说明 |
|---|---|
| `GET /api/data/manifest` | 清单：7 个白名单文件的名称 / 大小 / SHA-256 / 修改时间 |
| `GET /api/data/file/{name}` | 文件字节流，响应头带 `X-DIP3-Sha256` |

- 只认 `DataCatalog` 白名单里的 7 个标识，`settings` / `dezhou-favorites` / 任何拼出来的路径一律 404；
- 可选共享口令：后台「系统设置」写入 `dataShareToken` 后，请求须带 `?token=` 或 `X-DIP3-Token` 头，否则 401；
- 管理员仍按原流程在服务器上做后台导入，分发接口自动反映最新内容（清单即时计算，无需手动同步）。

**客户端**（后台新增「数据更新」页，位于「德州物价」与「系统设置」之间）：

1. **数据源**：填服务器地址（`10.0.0.8:3210` 或完整 URL）、共享口令、「启动时自动检查」开关；
2. **更新内容**：点「检查更新」列出 7 个文件的差异（状态 / 本机 / 服务器 / 服务器时间 / 存放位置），
   只下载不一致的文件；「立即更新」→ 下载到 `data/.staging/` → 逐个校验 SHA-256 →
   备份被覆盖文件到 `data/_backup/<时间戳>/` → 原子上位替换 → `AppState.ReloadAll()` 热重载（免重启）；
3. **备份与回滚**：任选历史备份点整体还原，还原前的版本同样会被备份；
4. **离线更新包**：导出 / 导入 `manifest.json + files/*` 的 zip，给上不了网的机器，效果与在线更新一致；
5. **启动静默检查**：配置了数据源且开关打开时，启动后在后台查一次，有更新用托盘气泡提示（不自动改数据）。

**改动文件**：新增 `Core/DataCatalog.cs`、`Core/DataUpdateClient.cs`、`Desktop/Views/Admin/AdminDataView.xaml(.cs)`；
修改 `Core/AppState.cs`（`ReloadAll`）、`Core/AppSettings.cs`（`DataSourceUrl` / `DataShareToken` / `AutoCheckUpdate` / `LastUpdateAt`）、
`Core/Infrastructure.cs`（`ReadJsonFile` 增加「刚被替换就重读」的重试与共享模式）、
`Web/WebRouter.cs`（两个分发接口）、`Desktop/AdminWindow.xaml(.cs)`、`Desktop/TrayIcon.cs`（`Balloon`）、
`Desktop/MainWindow.xaml.cs`（启动静默检查）、`Desktop/Probe.cs` + `App.xaml.cs`（`--probe-admin` 离屏取样）、
`Desktop/SelfTest.cs`（67→73 项）。

**验证**：编译 0 警 0 错；自检 73/73 连续 10 轮全绿（新增 6 项，其中两项是
**本地回环服务上跑通的真实 HTTP 全链路**：检查→差异→下载→校验→备份→替换→回滚，以及更新包导出/导入）；
dotnet test 98/98；真机起服务实测：无口令 401 / 错口令 401 / 正确口令（查询串与请求头）200 /
白名单外 404 / 路径穿越 404，7 个文件逐个下载与本地字节一致；新页离屏渲染版式正常；
绿色版 zip 75.7 MB（286 个文件）已重打并重启。

**顺手修的一个隐患**：`Js.ReadJsonFile` 原来对「刚替换完立刻重读」没有任何容错 —— 杀软实时扫描
短暂抓住新文件时，读失败会被静默吞掉，轻则设置读回默认值、重则整个数据库变空。现在以
`FileShare.ReadWrite` 打开并对瞬时 IO 异常重试 4 次，这条路径正是数据分发中心「替换 → ReloadAll」必经之路。

**使用（三步）**：
1. 数据主库那台机器跑 `Dip3Grouper.Web`（防火墙放行 3210 入站），照常后台导入更新数据；
2. 其他机器：后台 → 数据更新 → 填 `http://<主库IP>:3210`（可选共享口令）→ 保存配置 → 检查更新 → 立即更新；
3. 上不了网的机器：在主库上「导出更新包…」，拷过去「导入更新包…」。

## 九、服务端怎么开（部署与启动）

服务端就是 `Dip3Grouper.Web`，它同时是「数据主库」和「网页版分组器」。两种开法：

### 9.1 绿色版（推荐，主库机器上用这个）

```bat
:: 在开发机上打一次包
publish-web.bat
```

产出 `dist\DIP3-Web\`（自包含，不依赖 .NET 运行时），打成 `dist\DIP3-Server-win-x64.zip`（57 MB）拷到主库机器：

1. 整个文件夹解压到任意位置（如 `D:\DIP3服务端`）—— 必须整体解压，exe 需要同目录的 `config\`、`data\`、`web\`；
2. 双击「**启动 DIP3 数据服务端.bat**」。窗口会打印本机可用的访问地址（含局域网 IP），这个窗口要一直开着；
3. 访问 `http://localhost:3210`（分组器界面）、`/admin`（后台）；其他电脑填 `http://<局域网IP>:3210`。

启动脚本会把 `ipconfig` 里的 IPv4 直接列出来，省得自己去查机器 IP。换端口：`启动 DIP3 数据服务端.bat 3220`。

### 9.2 源码方式（开发机上）

```bat
run-web.bat 3210
```

脚本优先用 `src\Dip3Grouper.Web\bin\Release\net8.0\Dip3Grouper.Web.exe`，没有才回落到 Debug；数据目录默认取工程根（也可用环境变量 `DIP3_HOME` 指定）。

### 9.3 ⚠ 一个必须知道的坑

**`Release` 产物不会自动跟着改**。本轮新增的 `/api/data/*` 接口如果只编过 Debug，直接跑 `run-web.bat`（它优先认 Release）会跑到**旧 exe**，客户端「检查更新」必定失败 —— 现场表现是 manifest 接口 404。

已在本轮重新 `dotnet build -c Release` 并重发 `dist\DIP3-Web`，因此现在的绿色包是带分发接口的。以后凡是改过 Web 端代码，**发布前务必重编 Release**（`publish-web.bat` 内部会做，直接用它就不会踩）。

### 9.4 防火墙（只做一次）

Windows 防火墙默认拦 3210 入站：

```
控制面板 → Windows Defender 防火墙 → 高级设置 → 入站规则 → 新建规则
  → 端口 → TCP → 特定本地端口 3210 → 允许连接 → 全部勾选 → 命名「DIP3 数据服务」
```

### 9.5 验证记录（2026-10-07 实测）

绿色版 `dist\DIP3-Web` 起在 3210，不带 `--home` 自动识别数据目录：

| 请求 | 结果 |
|---|---|
| `/` 首页 | 200 |
| `/admin` 后台 | 200 |
| `/api/data/manifest` | 200，7 个文件（路径与大小正确） |
| `/api/data/file/settings` | 404（白名单外） |
| `/api/data/file/..%2Fsettings.json` | 404（路径穿越） |
| `/api/data/file/guifan`（11 MB） | 下载字节与本地 SHA-256 完全一致 |

另有 `publish-web.bat` 内置的第 5 步冒烟测试（发布时自动在 3399 端口起一次、请求 manifest、再关掉），本次输出 `[OK] manifest reachable, files=7`。

### 9.6 网页后台同步跟进（2026-10-07）

主库机器用浏览器访问 `/admin` 时看到的界面（`web/admin.html`）此前停留在 Node 时代，只有 4 页且概览简陋，
与桌面端后台（7 页）差距明显。本轮已补齐：

| | 补齐前 | 补齐后 |
|---|---|---|
| 侧栏 | 概览 / 病种库管理 / 立项指南 / 映射与灰码 | 增加 **德州物价**、**系统设置**（共 6 页，见 9.7） |
| 概览 | 映射统计 2 卡 + 快捷入口 | **四张数据卡**（病种库 / 映射表 / 立项指南 / 德州物价，含条数、导入时间、数据来源、数据文件）+ 病种库与立项指南各区段条数胶囊 |
| 德州物价 | 无 | 按文号导入（覆盖该批 / 追加）、模板、导出当前筛选、批次胶囊筛选、明细增删改、**类别使用说明**维护 |

服务端相应新增 `/api/admin/dezhou` 系列接口（列表 / 批次 / 模板 / 导出 / 导入 / 增删改 / 使用说明），
业务逻辑复用 Core 的 `DezhouPriceStore` 与 `AdminService`，与桌面端**同一份实现**。

「数据更新」页不入网页端：那是客户端拉数据的功能，浏览器用户直接读主库数据。

网页端可用 `?p=` 直达某一页，如 `http://<IP>:3210/admin?p=dezhou`。

### 9.7 网页后台的登录与「系统设置」（2026-10-07 追加）

补 9.6 时发现一个**安全缺口**，本轮一并修掉：

**问题**：`loginEnabled` 只在 `MainWindow.xaml.cs` 的「点『后台管理』按钮」处生效，守的是**桌面端**；
`WebRouter.cs` 里跟口令有关的只有 `dataShareToken`（那是给 `/api/data/*` 分发接口用的）。
结果是 **40 多个 `/api/admin/*` 接口零鉴权** —— 局域网里任何人打开 `http://<主库IP>:3210/admin`
都能导入病种库、改映射表、删物价。而 `settings.json` 里 `loginEnabled=true`、口令也已非默认值，
**看起来像设了密码，实际网页后台是敞开的**，这个误判本身比缺口更危险。

**修法**（口令复用桌面端同一套 PBKDF2，不新建账号体系）：

| 设计点 | 取值 | 理由 |
|---|---|---|
| 鉴权范围 | 仅 `POST /api/admin/*`（`login`/`logout` 除外）+ `GET /api/admin/settings` | 医院里多数人只是想看数据，让他们先登录纯属添堵；模板/导出是只读，也放开 |
| 会话 | 8 小时，Cookie `dip3_admin`（HttpOnly + SameSite=Lax），另认 `X-DIP3-Admin` 头 | 纯内存、**不落盘** —— 令牌写进文件会跟着绿色版目录被拷走、被分发 |
| 口令校验 | `SettingsStore.VerifyLogin`（PBKDF2-SHA256 / 10 万次） | 与桌面端共用 `settings.json`，改一处两端一致 |
| 登录失败 | 按来源 IP 计数，连续 5 次锁 60 秒，成功清零 | 按 IP 而非全局，免得有人误输几次把管理员一起锁在门外 |
| 改口令时 | `KeepOnly(当前会话)`：本人留在原地，其他人立刻掉线 | 已经证明身份的人不该被自己的操作踢出去 |
| 关闭校验时 | `WebSession.Clear()` | 留着无主会话没有意义 |

**本轮抓到并修掉的真 bug**：锁定到期后失败计数不归零 → 计数永远停在阈值上 →
**之后每一次尝试都立刻触发新锁定，等于输错 5 次就永久锁死**，管理员自己都进不来。
自检里一次误输口令立刻显示「已锁定 60 秒」才暴露出来。修法是到期（或超过 10 分钟冷静期）时把计数清零，
并补了 `tests/Dip3Grouper.Tests/WebSessionTests.cs` 做**确定性回归**（把 `LockTime` 调成 60ms 验证这条分支，
不必真等 60 秒）。

**网页端「系统设置」只做三项**（判过一遍，见 9.6 的取舍逻辑）：

| 卡片 | 内容 | 为什么网页端需要 |
|---|---|---|
| 基本设置 | 软件名称、单位/副名 | 网页标题与侧栏品牌跟随；此前 Web 端**零引用** `AppName`，属新增接线 |
| 后台登录 | 开关 / 账号 / 口令 | 就是上面这套鉴权；不搬过来的话改口令得去装桌面客户端 |
| 立项指南参数 | 项目类别、计价单位 | 被 `AdminLixiangView` 用作下拉候选，原先网页端**取不到**，属功能缺失 |

「界面主题」「关闭时最小化到托盘」仍留在桌面端——网页端有独立样式，托盘是 Windows 概念。

**验证**：
- 接口实测 52 项断言全绿：只读免登录 / 未登录写 401 / 错口令 401 / 登录后写通 / 退出后失效 /
  `X-DIP3-Admin` 头可用 / 限速 429 / 锁定到期自动解锁 / 改口令会话收敛 / 关闭校验后放行 /
  设置项往返 / 使用说明往返（原值 9 条 → 改成 2 条 → 还原 9 条，**未污染真实数据**）
- jsdom 真跑页面：只读内容全部渲染 → 进设置页被拦并弹登录框 → 错口令提示 → 登录成功后表单填充 →

- `dotnet test` **108/108**（新增 10 条会话用例）

### 9.8 前台消息推送（2026-10-07 追加）

**诉求**：「前台增加消息，可在网页服务端后台推送信息」。

**为什么不用 WebSocket / SSE**：主库机器是「绿色版解压即用、双击 bat 起服务」的形态，前台页面可能挂着
一整天也可能只开两分钟。60 秒轮询一次的请求量（几 KB JSON）在医院内网完全可忽略，
却换来**零额外依赖、无长连接、进程重启不掉线**——出问题时看日志就能定位，不用调连接状态。
所以走「**轮询 + 版本号**」：`data/notice.json` 的 `rev` 每次落盘递增，前台只需比 `rev` 决定要不要重绘。

**三种到达强度**（后台按需选，前台不用配）：

| 后台设置 | 前台表现 | 适用 |
|---|---|---|
| 钉住 | 导航栏下方**常驻横幅**（单行 + 「查看」展开全文） | 长期须知、制度变动 |
| 不钉 | 只进「🔔 消息」抽屉；本次会话首次打开页面时**自动展开一次** | 一般通知 |
| 不勾「立即发布」 | 前台完全看不到（草稿） | 起草中、待审 |

**生效期**：留空＝立即 / 长期；填了则到点自动出现、过期自动消失，用**本地时间**（`yyyy-MM-ddTHH:mm`，
`datetime-local` 原生格式，不做时区换算——排班通知本就是「本地墙上的钟」语义）。
提前把「10 月 8 日起执行新病种库」写好，当天不用专人守着点发布。

**逐台浏览器独立**：已读、以及「本机关闭某条」（条目的 ✕）都只写各自 localStorage，
不落服务端、不影响别人——避免「有人点了关闭，全院都看不到」这类事故。
识别键是 `id + updatedAt`，后台改了内容会自动重新变成本机未读。

**安全边界**（沿用 §9.7 的「只守会改数据的」原则，但有两处必要加严）：

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `GET /api/notice` | **免登录** | 前台页面本来就不需要登录；返回值**只有前台要显示的字段** |
| `GET /api/admin/notices` | **要登录** | 含未发布草稿 → 属未公开运营信息（与 `GET /api/admin/settings` 同类处理） |
| `notice-save` / `-toggle` / `-delete` / `-clear` | 要登录 | `POST /api/admin/*` 默认已守 |

前台视图刻意**不含** `enabled` / `startAt` / `endAt` —— 排期与发布开关是运营内部信息，
没必要让每个浏览器都拿到（自检里有一条硬断言守着这点）。

**改动文件**：新增 `Core/NoticeStore.cs`（`Notice` / `NoticeFile` / 生效期过滤 / 参数校验 / 版本号）、
`AppPaths.NoticeFile`、`AppState.Notice`；`WebRouter` 加 6 个接口 + `NeedsAdminAuth` 加一行；
`web/index.html` 加消息中心（铃铛 + 抽屉 + 横幅 + 轮询）、`web/admin.html` 加「消息推送」页；
`SelfTest` 新增第 74 项。

**验证**：
- 自检 **74/74**（新增项覆盖：3 条消息中只 1 条对前台可见、前台 JSON 不含排期字段、
  5 类非法入参被拦、停用即时生效、版本号递增与幂等、落盘往返一致）
- 隔离实例（3233 端口 + 临时工程副本）**接口断言 24/24**：未登录读前台 200 / 读后台 401 /
  四个写接口 401 / 登录后可发布 / 非法输入 400 / 停用后前台立即为空 / 删除与清理草稿 / 退出后 401
- jsdom 真跑两个页面：前台 **19/19**（角标、横幅、自动展开、已读清零、本机关闭、全部已读、

## 十、公共设置跟随与「发布不再冲掉设置」（2026-10-07 追加）

### 10.1 起因：两个看起来互不相干的现象

用户在**服务端后台**设了「单位副名」，随后看**桌面客户端**没变化；
同时**网页后台 → 系统设置 → 立项指南参数**里两个框是空的，可前台立项指南页明明有类别/单位。

排查后是两个独立原因：

| 现象 | 真正原因 |
|---|---|
| 客户端不跟随服务端 | 服务端与客户端是**两份独立部署**，各有 `data/settings.json`，本来就不通 |
| 服务端副名"没生效" | 上一轮 `publish-web.bat` 把整个输出目录删掉再用仓库 `data\` 覆盖，**把刚设置的副名冲掉了** |
| 立项参数框空、前台有 | 网页后台直接读 `settings.json` 里的参数表（没配过就是空）；桌面端参数页在空表时会回填"现有数据去重值"，网页端漏了这一步 |

### 10.2 先修的坑：发布脚本会覆盖运行期数据（重要）

`publish-web.bat` / `publish-desktop.bat` 原逻辑：

```
rmdir /S /Q <输出目录>              ← 删掉整个部署
xcopy 仓库\data  <输出目录>\data    ← 用仓库那份盖上去
```

`data\` 里混着两类东西，必须分开对待：

| 类别 | 文件 | 发布时 | 理由 |
|---|---|---|---|
| 可再生的业务数据 | `mappings.json`、`lixiang.json`、`dezhou-price.json`、`guifan.json`、`config-meta.json`、`zonghe.json`、`config/dip3-config.json` | **覆盖** | 仓库是唯一源头，部署目录那份可能是旧的 |
| 运行期本机数据 | `settings.json`、`notice.json`、`dezhou-favorites.json`、`_backup\` | **保留** | 只存在于部署目录，删了就真没了 |

修复：发布前把后者暂存到 `%TEMP%\dip3_web_keep` / `%TEMP%\dip3_desktop_keep`，
`[6/7]` 步放回；失败路径也尽力归还（并保留暂存目录供手工兜底）；
上一步失败留下的未归还暂存，不会被下一次运行误删。

实测：先经 API 把副名写成「平原县中医院」→ 停服 → 重跑 `publish-web.bat` →
部署目录 `data/settings.json` 里副名仍在（仓库那份仍是 `null`，对照正确）→ 重启服务后
`/api/settings/public` 正常返回。

> 另一条实战教训：发布时程序仍在运行会导致 `dotnet publish` 报 `MSB3027/MSB3021`
> （dll 被占用）。这次就先撞上了——`dist/DIP3-Desktop` 被清到一半、`data\` 缺失，
> 靠暂存目录 + 脚本的失败归还才恢复。**发布前先退出程序。**

### 10.3 公共设置跟随：服务端当配置中心

让展示类设置可以从服务端统一下发到各台客户端，不必逐台手改。

| 字段 | 是否下发 | 说明 |
|---|---|---|
| 软件名称 / 单位副名 | 是 | 客户端窗口标题、启动页品牌区 |
| 立项指南参数（项目类别 / 计价单位） | 是 | 客户端新增/编辑立项项目时的下拉候选 |
| 后台登录账号口令 | **否** | 下发口令哈希等于把全院后台交出去 |
| 界面主题 / 关闭到托盘 / 数据源地址 | **否** | 本机私有，各人各机自定 |
| 德州物价「常用收藏」 | **否** | 每台机器各不相同 |

- **通道**：`GET /api/settings/public`（只读、免鉴权，只回上表"是"的字段）。
  该接口原本只回软件名称/副名/品牌短名供标题渲染，这次补上两个立项参数字段，
  一个接口同时服务"前台渲染"和"客户端跟随"。
- **客户端**：`Core/PublicSettingsClient.cs`（`FetchAsync` / `SyncAsync` / `Apply`）。
  开关 `settings.json → followServerSettings`（默认开，可在「后台管理 → 数据更新」里关）。
- **时机**：启动时静默同步一次；「立即更新」数据成功后顺带同步；也可点「立即同步设置」手动触发。
  有改动时写盘 + `App.NotifySettingsChanged()`，窗口标题与品牌区**立刻**跟着变，不用重启。
- **语义（关键设计点）**：**服务端有值才下发**。服务端某字段为空表示"管理员没在这台服务上配"，
  此时保留客户端自己的值 —— 避免服务端漏填一项就把全院客户端的配置清空，
  也让"客户端没配 → 自动取现有数据"的语义两边一致。
  反之，服务端把副名从 A 改成 B，开启跟随的客户端下次启动就会变 B。

### 10.4 网页后台设置页：空参数表时回填现有取值

### 11.3 共享口令的设置入口与边界

### 11.4 顺带修掉的三个偶发（发布冒烟自检 75/76 的根因）

这轮发布冒烟三次出现「不同项随机失败」，逐一排查后是三个独立问题：

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 设置往返读回旧值，磁盘=「旧业务值+新 updatedAt」 | **运行中的客户端实例**（管理员的桌面客户端）用它内存里的旧设置写回了同一份 `settings.json`，与自检的写读断言互踩 | 自检第 67/71 项改到**独立临时根目录**，不再碰真实部署的设置文件；另补 `SettingsWriteStressTests`（单进程 300 次写读压测，证明写路径本身可靠） |
| 2 | 写盘偶发抛 IO 异常 | `Js.WriteJsonFile` 零容错（读侧上一轮已加重试，写侧漏了）——Defender/索引服务短暂独占刚落盘的文件 | 写侧补同一套退避重试（4 次、80ms 递增） |
| 3 | 回滚后文件内容不对（隔离目录里也偶发） | **真 bug**：`Install` 的备份目录用秒级时间戳命名，「更新→立即回滚」落在同一秒时，Restore 会用「还原前的内容」覆盖上一轮备份，回滚拷回错误内容 | 目录重名时追加 `-N` 序号 |

修复后自检连跑 4 遍全绿（76/76），`dotnet test` 109/109（新增 1 条压测）。
